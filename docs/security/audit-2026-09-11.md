# Security audit, 2026-09-11

## Scope

`spotiflac-lidarr-proxy` at `df64bd3`, the Go service only. Threat model: an
operator who exposes the HTTP surface beyond a private network. In scope:
route-by-route authentication, SSRF through the callback relay and the
configurable upstream URLs, argument injection into the `spotiflac-cli`
subprocess, path traversal out of `SPF_OUTPUT_DIR`, and secret disclosure in
responses and logs.

Method: read of the route wiring and auth middleware, static trace of every
`exec.Command*` and filesystem sink, then a running instance probed directly.
Probes ran against a local build on ports 18484-18486 with a throwaway key and
a `/bin/echo` stand-in for the CLI. No third-party host was contacted.

## Findings

| # | Severity | Area | Summary |
|---|----------|------|---------|
| 1 | LOW | SSRF | `/api/verify-relay` accepts any loopback `host:port` when the state is unrecorded |
| 2 | LOW | Info disclosure | `/metrics` was unauthenticated (fixed in this pass) |
| 3 | INFO | Info disclosure | `/health`, `mode=version` and `t=caps` are unauthenticated by design |

### Finding 1: SSRF: unrecorded-state fallback in `/api/verify-relay`

* Severity: LOW
* Confidence: 8
* Attacker: anyone who can reach the port; no credentials.
* Evidence: `internal/api/verify_relay.go:147` — `resolveUpstream` prefers a
  recorded callback, and when `state` is unknown falls through to
  `validateCallbackURL(supplied)`, which requires only scheme `http`, path
  exactly `/session-grant`, and a loopback host. The port is unconstrained.
  `TestVerifyRelayAllowsUnrecordedLoopbackGrantCallback` shows this is
  deliberate.
* Impact: an unauthenticated caller can make the process issue
  `GET http://127.0.0.1:<any port>/session-grant?...&grant=<attacker string>`.
  In the deployed topology the proxy shares gluetun's network namespace with
  qBittorrent, slskd, aria2, kapowarr, searxng and i2pd, so "loopback" is
  wider than it sounds. The fixed path makes this a port-existence oracle
  rather than a general request primitive: nothing else on those ports serves
  `/session-grant`. No response body is relayed back
  (`TestVerifyRelayNeverReflectsUpstreamBody`).
* Fix: drop the fallback and require a recorded state, which is exactly what
  the sibling handler `/verify/callback` already does
  (`internal/api/verify/handler.go:55`, "never to whatever an inbound request
  merely claims upstream_cb is"). The two endpoints disagree today; the
  stricter one is right. Not changed in this pass because the relay is the
  path an external solver's browser uses and tightening it needs a test
  against a real solve.

### Finding 2: `/metrics` reachable without the API key — FIXED

* Severity: LOW
* Confidence: 10
* Attacker: anyone who can reach the port; no credentials.
* Evidence, before the fix:

      $ curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:18484/metrics
      200

* Impact: job counts by status and service, queue depth, download duration
  histograms and the build version. No secrets, but it is free reconnaissance
  on a service people do put on the internet, and nothing in Lidarr scrapes
  it.
* Fix: applied. `/metrics` now requires the key via `api.APIKeyOnly`, which
  has no mode/type exemptions at all. `SPF_METRICS_REQUIRE_AUTH=false` restores
  the old behaviour for a Prometheus that cannot send a key. Verified:

      no key      401
      wrong key   401
      correct key 200
      opt-out     200

### Finding 3: unauthenticated endpoints by design

* Severity: INFO
* `/health` stays open because the container healthcheck calls it
  (`docker-compose.yml:73`). It returns `{"break_until","session_expires_at",
  "status"}` and, when unhealthy, check names (`database`, `cli_executable`,
  `disk_space`) — no paths, no secrets.
* `mode=version` and `mode=auth` are skiplisted because Lidarr probes them
  before a key is configured; requiring one breaks the Test button.
* `t=caps` is skiplisted for the same reason. It routes to `CapsXML`, which
  never receives the API key. The one code path that embeds the key in output
  (`indexer.NewznabXML`, grab links) is reachable only with a valid key, and
  the unauthenticated empty-results path passes `nil` results so no link is
  generated.

## Verified clean

**Authentication coverage.** Every route probed without a key against a
running instance. 401 on `queue`, `history`, `get_config`, `get_cats`,
`addurl`, `addfile`, `warnings`, `server_stats`, `fullstatus`, `pause`,
`resume`, and on newznab `search`, `music`, `details`, `get`. 200 only on the
four documented exemptions above.

**Auth bypass regressions.** The August 2026 bypass (`&t=caps` appended to a
`mode=` request) is closed, and so is its mirror image:

    /api?mode=queue&t=caps        401
    /api?mode=get_config&t=caps   401
    /api?mode=addurl&t=caps       401
    /api?mode=history&t=caps      401
    /api/newznab?t=search&mode=version   401
    POST /api  (mode=queue in body)      401

**Key comparison.** `crypto/subtle.ConstantTimeCompare`
(`internal/api/middleware.go:69`). An unset `SPF_API_KEY` is a startup error
(`internal/config/config.go:167`), so there is no "no key configured means no
auth" state.

**Argument injection into `spotiflac-cli`.** Every `exec.Command*` passes an
argv slice; no shell. The one `sh -c` is `SPF_SESSION_RENEW_CMD`, operator
input by definition. The only request-controlled value reaching argv is the
Spotify URL, behind a fully anchored allowlist
(`internal/config/spotify_url.go`). All rejected with 400:

    --output-dir=/tmp/pwn
    https://evil.com/album/x
    https://open.spotify.com@evil.com/album/x
    https://open.spotify.com.evil.com/album/x
    https://open.spotify.com/album/../../etc/passwd
    file:///etc/passwd
    http://169.254.169.254/latest/meta-data/

**Path traversal out of `SPF_OUTPUT_DIR`.** `PrepareJobDir` and `CleanupJob`
both reject `..`, `/` and `\`; `JobDir` is only reached through them. Probed
the delete endpoint with a canary directory outside the output dir:

    ../../../tmp/spf-canary            canary survived
    ..%2f..%2f..%2ftmp%2fspf-canary    canary survived
    SABnzbd_nzo_../../tmp/spf-canary   canary survived
    /tmp/spf-canary                    canary survived

**`pkill` pattern.** `internal/api/sabnzbd/browsers.go` execs
`pkill -9 -f <pattern>` from a hardcoded list (`chromium`,
`chrome_crashpad`, `_bridge.js`). No request input reaches it.

**Secret handling in logs.** `redactAPIKey` rewrites the `apikey` query
parameter per `&`-segment rather than through `url.ParseQuery`, so a decode
failure elsewhere cannot suppress redaction
(`internal/api/middleware.go:102`).

**SSRF via `/verify/callback`.** Relays only to the exact URL the CLI
recorded, returns 410 when nothing is pending, clears the store, and never
reflects the upstream body.

**Configurable upstream URLs.** `SPF_TIDAL_API_URL`, `SPF_QOBUZ_API_URL` and
`SPF_TIDAL_API_FALLBACK_URLS` are operator-set environment variables, not
request input.

## Shape of the risk

The application-level surface is in good order: the interesting sinks are all
guarded, and the two historical holes here (unvalidated relay target, the
`t=caps` bypass) were found before and stayed fixed under re-probing.

The real risk is not a bug in this code, it is the deployment assumption. The
API key travels as a query parameter over plain HTTP, which means every
reverse proxy, access log and browser history between Lidarr and this service
holds the credential. That is fine on a private bridge and unacceptable on a
public address, and no amount of route hardening changes it. `SECURITY.md`
now says so rather than leaving it implied.
